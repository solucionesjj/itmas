# ADR-0011: Multiplatform collection agent — Python, core/platform split, macOS LaunchDaemon

- **Status**: Accepted
- **Related**: `spec.md` §5/§10, `agent.md` §1/§14 (collection agents documented as out of scope for backend/frontend development); ADR-0003 (node authentication); ADR-0004 (secret hashing); `agent/docs/ARCHITECTURE.md`

## Context

`spec.md`/`agent.md` explicitly treat the OS-level collection agent as a pre-existing external input to IT-MAS ("se asume que envían datos a la API") and out of scope for Fase 1 backend/frontend development. The project owner explicitly decided to build one now anyway, in a dedicated `agent/` folder separate from `backend/`/`frontend/`, with the explicit goal of a **single codebase reusable across macOS, Windows, and Linux** rather than a macOS-only tool. This is a deliberate scope decision, not an oversight of the existing constraint, and is recorded here per the Decision Framework (agent.md §13, rule 4 — affects nothing in the backend's API contract itself, but is an architectural decision worth an ADR regardless).

## Decision

- **Language: Python 3.11+.** Initially scoped as Swift (best native macOS API depth) under the assumption of frequent invocation and a macOS-only target. Both assumptions changed during design: the user requires only a once-daily (+ on-demand) run, making Swift's low-overhead-per-invocation advantage irrelevant, and explicitly wants one codebase reused for Windows/Linux agents later, where Swift has poor-to-no practical support. `psutil` gives genuinely uniform CPU/memory/disk/session/network primitives across all three OSes, letting most of the core avoid any per-OS code at all.
- **Core/`PlatformBackend` split**: everything `psutil`/stdlib already resolves uniformly (storage volumes, CPU/memory, active sessions for `last_login`, local IP) lives directly in OS-agnostic `collectors/`. Only what genuinely differs per OS (hardware/serial inspection, installed-application enumeration, local user/group directory, credential storage, service installation) goes through a `PlatformBackend` protocol, one implementation class per OS. Adding a new OS is implementing that one class — zero changes to collectors, normalization, networking, persistence, or the CLI.
- **macOS backend implemented completely now; Windows/Linux are documented `NotImplementedError` stubs** with the intended API/tool per method recorded in each stub's docstring (WMI/registry + Task Scheduler for Windows; DMI sysfs/`/proc`/`pwd`+`grp` + systemd timer for Linux) — explicit user decision, to avoid an unbounded scope in this pass while keeping the extension point real and reviewed.
- **macOS runs as a LaunchDaemon**, not a LaunchAgent: a LaunchAgent only exists inside a logged-in session, which cannot satisfy "sees every local user regardless of who (if anyone) is logged in" or "runs at 9am even if no one has logged in yet."
- **Scheduling is once-daily at a configurable hour (default 9:00 local time), not a persistent process**: `StartCalendarInterval` (launchd's own anacron-like wake catch-up) + `RunAtLoad` (catches a fresh install/reboot after 9am the same day) + an internal `scheduling.is_daily_run_due()` gate (the only piece that actually decides whether to run, testable with an injected clock) jointly implement "run daily, catch up if missed, support on-demand" without a resident process. `itmas-agent run --now` / `launchctl kickstart` cover on-demand.
- **Node API key storage: macOS System keychain** via the `security` CLI targeting `/Library/Keychains/System.keychain` explicitly — not the generic `keyring` package, whose macOS backend resolves against the *current user's login keychain*, which doesn't exist/isn't unlocked for a root LaunchDaemon running with no session. `CredentialStore` is defined as a `PlatformBackend`-scoped protocol so Windows (Credential Locker/DPAPI) and Linux (no equivalent always-on store — needs its own ADR when implemented) can each provide the right mechanism behind the same interface.
- **Universal2 (arm64+x86_64) macOS binary is built per-architecture then merged with `lipo`**, not via a single `pyinstaller --target-arch universal2` invocation — verified empirically that pip-installed C-extension dependencies (`psutil`) resolve to single-arch wheels even under a universal2 Python interpreter, and PyInstaller correctly refuses to fold a single-arch `.so` into a universal2 executable. `Scripts/macos/build.sh` builds one venv per architecture (the x86_64 one via Rosetta 2 on Apple Silicon) and fuses the two resulting binaries.

## Consequences

- The rich internal model (`itmas_agent/models.py`) already collects the full 7-category scope the user asked for (hardware, OS, applications, storage, users+groups+last_login, resources, network), independent of what the backend's current `/inventory` DTO accepts — see ADR-0012 for the transmission-side consequence of that gap.
- `last_login` and any notion of login/logout auditing is explicitly **not** attempted as a near-real-time `/access-events` feed in v1 — a once-daily cadence cannot usefully serve the off-hours-alerting use case that endpoint exists for (agent.md's `off_hours_access` rule assumes much more frequent reporting than once a day). `psutil.users()` is used only to populate the `last_login` field of the users snapshot, with an honest documented limitation (a session fully contained between two daily runs is invisible).
- Windows/Linux agents, when built, inherit the exact JSON contract and core module structure for free — the only new work is one `PlatformBackend` implementation and one OS-native service installer per platform, per the stub docstrings in `itmas_agent/platforms/{windows,linux}/backend.py`.
