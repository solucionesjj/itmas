# ADR-0016: Portal-based device provisioning and key rotation

- **Status**: Accepted — amends ADR-0003
- **Related**: ADR-0003 (Node/device authentication mechanism), ADR-0004 (secret hashing), agent.md §13 Decision Framework rule 4 ("¿Afecta contrato de API o modelo de datos? → Mantén compatibilidad; documenta con ADR")

## Context

ADR-0003 deliberately kept device provisioning and key rotation CLI-only (`npm run device:provision` / `device:rotate-key`), on the grounds that no such REST endpoint exists in the authoritative contract (`agent.md` §5.4 / `spec.md` §12) and inventing one would violate "no inventes endpoints fuera del spec."

The project owner has now explicitly asked to reverse that specific piece of ADR-0003: an Administrador should be able to create a device (obtaining its hostname/category/API key) and rotate an existing device's key directly from the Angular portal, without touching the CLI. This is a confirmed, deliberate scope decision by the person with authority to make it — not something inferred or assumed — so per the Decision Framework's rule 4 it is implemented and documented via this ADR rather than treated as an ambiguity to resolve conservatively.

## Decision

- **Two new endpoints, Administrador only**: `POST /api/v1/devices` (`{hostname, category}` → `201 {deviceId, hostname, category, apiKey}`) and `POST /api/v1/devices/:id/rotate-key` (no body → `200 {deviceId, apiKey}`, `404` if the device doesn't exist). Both carry a method-level `@Roles(ADMINISTRATOR)` that overrides `DevicesController`'s class-level `@Roles(ADMINISTRATOR, USER, AUDITOR)` (which still governs the pre-existing `GET /devices`) — `RolesGuard`'s `getAllAndOverride()` resolves the method-level declaration in preference to the class-level one, so this is a one-line-per-route override, not a new guard mechanism.
- **Reuse, not reimplementation**: both routes call `DevicesService.provision()`/`rotateKey()` verbatim — the exact same methods the CLI scripts already call. No key-generation, hashing, or persistence logic was duplicated; the only service-level change was widening `rotateKey`'s not-found case from a plain `Error` to `NotFoundException` so the REST layer can surface a real `404` (the CLI script's `catch` still handles it identically, since `NotFoundException` is still an `Error`). This preserves the one-time-reveal security property (plaintext key returned once, only its argon2 hash ever persisted) exactly as it already held for the CLI path — there was never a second place for that property to be re-implemented incorrectly.
- **`POST /devices` is the only endpoint in the entire API whose response body carries a plaintext `apiKey`** (mirroring the CLI's own scripts, and reports export's "only non-JSON-envelope endpoint" precedent from ADR-0008 as a similarly-flagged, deliberate one-off). It never appears in any other response, including `GET /devices` for that same device (`device-response.mapper.ts`'s `toDeviceResponse()` is untouched and still strips `apiKeyHash`; the two new endpoints intentionally bypass it entirely rather than being taught to sometimes include the key).
- **Audit logging**: two new `AuditLogAction` values, `create_device` and `rotate_device_key`, recorded via the same `AuditLogService.record(action, actorId, target, detail)` call convention every other mutation endpoint uses (`update_alert_rule`, `create_user`, etc.). `detail` for `create_device` holds only `{hostname, category}` — never the key or its secret half, matching the existing rule that audit `detail` must never contain credential material.
- **No logging of the plaintext key anywhere else**: confirmed there is no generic response-body-logging middleware/interceptor in this app (`AllExceptionsFilter` only logs `message`/`path`/`method`/`status` on error paths; the structured `JsonLoggerService` is only ever called explicitly, and no call site passes the key). The one-time-reveal property therefore holds through the full HTTP response path, not just at the service layer.
- **Frontend**: a "Crear dispositivo" button and a per-row "Rotar clave" icon button on the existing `devices-list` page, visible only when the authenticated user's role is `administrator` — the same inline `@if (authService.currentUser()?.role === ...)` pattern `shell.component` already uses for "Usuarios"/"Alertas", not a new mechanism. This is UX-only; the two new endpoints' own `@Roles(ADMINISTRATOR)` is the real enforcement (verified directly against the API, independent of the UI, during manual testing). A confirmation dialog precedes rotation ("la clave anterior dejará de funcionar inmediatamente"), and both flows end in a shared one-time-reveal dialog (full key, copy-to-clipboard, "no se mostrará de nuevo" warning) that is never reachable except immediately after a `201`/`200` from these two endpoints.

## Consequences

- **CLI scripts remain valid and unchanged** — `npm run device:provision`/`device:rotate-key` are not deprecated by this change; they remain the correct tool for out-of-band/scripted fleet bootstrap (e.g. bulk provisioning without a browser session), and now share their exact underlying implementation with the portal path, so the two can never drift apart in behavior.
- **Operationally, a new node can now be provisioned without shell access to the backend host** — closing the "out-of-band CLI step" friction ADR-0003 flagged as a deliberate tradeoff, at the cost of a wider blast radius if an Administrador account is compromised (an attacker with a stolen Administrador session can now mint working node identities from the browser, not just read/manage existing ones). This is judged acceptable because it is strictly narrower than what an Administrador could already do (full user management, alert-rule configuration) — no new privilege tier was introduced, only a new capability within the existing Administrador tier.
- **ADR-0003 is amended, not superseded**: its key format, argon2-hashing, dual-auth-mechanism, and "device must be provisioned before it can send data" decisions are all still in force and untouched. Only its "provisioning and rotation are CLI-only" clause is reversed. See the amendment note added directly to ADR-0003.
